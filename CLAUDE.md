# CLAUDE.md

Telegram-бот техподдержки Bitrix24: aiogram + LangGraph (RAG) + PostgreSQL/pgvector. Деплоится в Docker.

## В начале каждой сессии прочитать `ROADMAP.md`

`ROADMAP.md` в корне — источник правды по состоянию проекта и списку доработок с приоритетами (**P0** критично → **P3** тех.долг). Перед любой задачей, связанной с функциональностью бота, граф-агентом или базой знаний, прочитай его, чтобы понимать контекст и не дублировать уже зафиксированные пункты.

## Обновление `ROADMAP.md` — обязательно

- Закончил пункт → отметить `[x]` и коротко дописать, что именно сделано.
- Нашёл новую проблему / появилась идея → добавить пункт в нужный приоритет.
- Пользователь меняет приоритет ("это срочнее") → переносить пункт между секциями.
- Архитектурное изменение (новый/удалённый модуль, смена БД, нового внешнего сервиса) → отразить в разделе "Текущее состояние".

Приоритеты:
- **P0** — критично, ломает пользовательский сценарий.
- **P1** — высокий, заметные проблемы, но не полная блокировка.
- **P2** — средний, стабильность / качество.
- **P3** — мелочи, тех.долг, рефакторинг.

## Архитектура (коротко)

- `telegram_bot/` — aiogram-бот: `business_message` (клиенты через бизнес-аккаунт) + роутеры для специалиста и группы. Polling, опционально через прокси (`AiohttpSession`).
- `bitrix_qa_agent/` — LangGraph-граф QA: `check_new_intent` → `check_negative` → `need_reply_check` → `positive_acknowledgement_check` → `knowledge_required_check` → RAG (`identify_search_query` → `vector_search_articles` → `get_relevant_articles_ids` → `form_context` → `generate_answer`).
- `loader/` — отдельный сервис загрузки базы знаний (статьи + исторические диалоги) в Postgres с эмбеддингами.
- `media_recognizer/` — распознавание медиа (фото/голос/файлы → текст через LLM).
- `alembic/` (основная БД бота) и `alembic_articles/` (база знаний) — две независимые миграционные истории.
- LLM — через OpenRouter (`pro_model`, `lite_model`). Эмбеддер — свой клиент.

## Деплой

Образ собирается **локально через `buildx`**, пушится в Docker Hub, на сервере подтягивается через `compose pull && up -d`. **Не собирать на сервере**.

### Команды сборки + пуша (вызывать автономно, когда пользователь говорит "собери образ" / "запуши образ" / "собирай")

Архитектура — **`linux/amd64`** (под сервер `vvclubbitr-vps-1`). Репо в Docker Hub — `pr21109090/bitrix_qa`, тег — `multiarch` (исторически название, фактически amd64).

```bash
docker buildx build --platform linux/amd64 -t pr21109090/bitrix_qa:multiarch --push .
```

- Запускать из корня проекта (там, где лежит `Dockerfile`).
- `--push` означает публикацию в Docker Hub — действие необратимое, но пользователь явно авторизовал автономный вызов этой команды.
- Сборка займёт несколько минут (кросс-сборка под amd64 на arm64 хосте через эмуляцию). Запускать в фоне (`run_in_background`), потом мониторить.
- Если упадёт на `authentication required` — попросить пользователя выполнить `docker login` в его терминале (через `! docker login`).
- На сервер выкатывать **не моя зона** — пользователь сам делает `compose pull && up -d`.

## Время и логи

- В контейнере таймзона **UTC** (TZ не задана). Сервер и Telegram-UI — **MSK = UTC+3**. При чтении логов: `время_в_логе + 3ч = MSK`.
- `PYTHONUNBUFFERED=1` уже в Dockerfile — буферизации stdout нет.
- `docker logs --since "YYYY-MM-DDTHH:MM:00" --until "..."` принимает локальное время сервера (MSK), но в выводе таймштампы приложения остаются UTC. Перевод TZ контейнера на MSK — пункт в P2 ROADMAP.
