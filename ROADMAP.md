# Bitrix QA Bot — Roadmap

> Живой документ. Пополняется по мере обнаружения проблем и идей.
> Приоритеты: **P0** — критично, блокирует пользователей; **P1** — высокий; **P2** — средний; **P3** — мелочи и тех.долг.

---

## Текущее состояние

### Архитектура
- **`telegram_bot/`** — aiogram-бот для Telegram. Работает через бизнес-аккаунт (`business_message`), плюс роутеры для специалистов и группы. Polling через `AiohttpSession` (опционально с прокси).
- **`bitrix_qa_agent/`** — LangGraph-граф для QA. Пайплайн: проверка смены интента → проверка негатива → нужен ли ответ → положительный отклик → нужна ли БЗ → RAG (поиск статей, отбор, формирование контекста, ответ).
- **`loader/`** — отдельный сервис для загрузки базы знаний (статьи + примеры диалогов) в Postgres с векторными эмбеддингами.
- **`media_recognizer/`** — распознавание текста из медиа-сообщений (фото, голос и т.п.).
- **`alembic/`** + **`alembic_articles/`** — два набора миграций: основной для бота и отдельный для базы статей.
- **PostgreSQL + pgvector** — хранение чатов, сессий, сообщений и векторных эмбеддингов статей/диалогов.
- **Внешние LLM** — через OpenRouter (`pro_model`, `lite_model`), эмбеддер через свой клиент.
- **Деплой** — Docker-образ собирается локально через `buildx`, пушится в Docker Hub, на сервере `compose pull && up -d`.

### Что работает
- Приём сообщений клиентов через бизнес-аккаунт + команды специалиста.
- Распознавание медиа (через `media_recognizer`) — **по факту только фото**; голос/видео/файлы уходят на специалиста. ⚠️ Сейчас вероятно сломано из-за неверного ключа (см. P0).
- Двухрежимная сессия (AI / специалист) с переключением через `takeover` и при негативе.
- RAG-ответы на основе базы знаний (статьи) и базы исторических диалогов.
- Автоответ + ответ на положительный отклик + перевод на специалиста при негативе.
- Прокси для запросов к Telegram и эмбеддеру (для обхода блокировок).

Так как исключение не ловится (нет try/except и нет глобального error-хендлера, см. ниже), **клиент, приславший фото, не получает ответа, а само сообщение теряется** (медиа обрабатывается до сохранения в БД).

P1). Нужен `@dp.errors`-хендлер + защитная обёртка, которая при сбое фолбэчит на перевод на специалиста и логирует контекст. Это «зонтик» над несколькими симптомами (вкл. уже закрытый P0 про ретрай и P1 про сохранение).
  **Сделано:** AI-обработка вынесена в `_process_ai_message`, обёрнута в try/except в `handle_client_message` — при любом сбое лог + фолбэк на специалиста (по актуальной активной сессии, с учётом возможной смены интента). Плюс глобальный `dp.errors.register(on_unhandled_error)` в `bot.py` как последний рубеж.
